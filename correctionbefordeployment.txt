**Format:** Each item is a self-contained command or file edit you can paste into a fresh DeepSeek session. Every task ends with a **verify** step so you know it worked before moving on. Order matters — do them top to bottom.

**Convention:**
- 🔴 = blocker (don't skip, don't reorder)
- 🟠 = required for 15 concurrent users
- 🟡 = required before public DNS
- 🟢 = cleanup
- Each task is numbered `T01`, `T02`, … so you can say "do T07" in a fresh session.

### T16 🔴 Fix ID generation races
Add a counter table. In `backend/app/models.py`:
```python
class SequenceCounter(Base):
    __tablename__ = "sequence_counters"
    name = Column(String(50), primary_key=True)
    value = Column(Integer, nullable=False, default=0)
```
Then in `crud.py`, replace `generate_rm_id`, `generate_fg_serial`, `generate_po_token` with a single helper:
```python
def _next_seq(db: Session, name: str) -> int:
    row = db.query(models.SequenceCounter).filter(
        models.SequenceCounter.name == name
    ).with_for_update().first()
    if not row:
        row = models.SequenceCounter(name=name, value=0)
        db.add(row)
        db.flush()
    row.value += 1
    db.flush()
    return row.value

def generate_rm_id(db: Session) -> str:
    return f"RM-{_next_seq(db, 'rm_id'):06d}"

def generate_po_token(db: Session) -> str:
    from datetime import datetime
    date = datetime.utcnow().strftime('%y%m%d')
    n = _next_seq(db, f'po_{date}')
    return f"PO-{date}-{n:03d}"
```
For `generate_fg_serial`, same pattern keyed on the date.

**Verify:** Two parallel curls to `/master/inventory/` POST — get two distinct RM IDs.

## The 15-user bottom line

For 15 concurrent users, the *minimum* set that actually matters is:

- **T05** (auth on every route) — otherwise "concurrent" includes attackers.
- **T15** (row locking) — prevents lost inventory updates.
- **T16** (ID sequence races) — prevents duplicate PO tokens.
- **T17** (sync handlers) — prevents event-loop stalls.
- **T18** (pool 20/30) — 15 users × a few requests each needs headroom.
- **T19** (gunicorn 4 workers) — one uvicorn worker = one core = ~5 real concurrent users.
- **T20–T22** (kill full scans + indexes) — otherwise latency grows with every order.
- **T30** (load test) — proves it.

Everything else is polish. If you're short on time, do those nine, deploy, and circle back for the rest.
